## 제약

데몬은 두 개의 문으로 같은 기능을 제공한다 — 같은 머신 안에서만 통하는 유닉스 소켓과, 루프백 TCP 포트다. 두 문에 적용되는 인증 규칙이 다르다.

- **유닉스 소켓**: 인증을 요구하지 않는다. 같은 머신에서 소켓 파일에 접근할 수 있다는 사실 자체가 신뢰의 증거로 간주된다(로컬=신뢰). CLI 가 주로 이 경로를 쓴다.
- **TCP 리스너**: 요청자가 토큰을 가지고 있음을 증명해야 한다. 토큰은 **헤더(`X-Clawket-Token`)** 또는 **세션 쿠키(`clawket_session`)** 둘 중 하나로 제시할 수 있고, 둘 중 하나만 맞아도 통과한다. CLI·외부 도구는 헤더를, 브라우저로 뜬 웹 대시보드는 쿠키를 사용한다.

토큰은 **데몬을 켤 때마다 새로 생성**되어(재시작마다 회전) 파일로 기록되며, 토큰 파일은 소유자만 읽을 수 있는 권한으로 보관된다.

쿠키 기반 인증은 교차 사이트 위조(CSRF) 표면을 동반하므로, 상태를 바꾸는 요청(생성·수정·삭제)에 대해서는 추가로 **출처 검사(Origin/Referer 가 데몬 자신의 출처와 일치하는지)** 를 요구한다. 단, 파일 토큰을 헤더로 제시한 요청은 이미 같은 머신에 대한 소유 증명이므로 이 출처 검사를 면제한다. 또한 헬스 체크 경로와 SPA 부트스트랩에 필요한 정적 자원(인덱스·에셋·아이콘)은 인증 면제 경로로 둔다 — 인덱스 응답이 바로 쿠키를 발급하는 통로이므로 스스로 쿠키를 요구할 수 없기 때문이다.

## 깨지면 무슨 일이 일어나나

규칙이 약해지면 두 방향으로 위험이 생긴다. TCP 인증이 무력화되면 루프백 포트에 닿을 수 있는 프로세스(또는 공개 바인드가 함께 풀렸을 때 외부 클라이언트)가 토큰 없이 작업 상태·지식·감사 기록을 읽거나 바꿀 수 있다. 반대로 상태 변경 요청에 대한 출처 검사가 빠지면, 사용자가 방문한 악성 웹페이지가 브라우저에 남은 세션 쿠키를 빌려 데몬에 위조 요청을 보낼 수 있다(CSRF). 토큰 회전(재시작마다 새 토큰)이 무너지면, 한 번 유출된 토큰이 영구히 유효해진다.

이 제약은 같은 머신 안(소켓·CLI)과 브라우저(웹 대시보드) 사이의 경계를 가로지르므로, 한쪽 클라이언트만 보고 규칙을 바꾸면 다른 쪽이 깨진다.

## 코드에서 어떻게 강제되나

TCP 리스너에만 인증 미들웨어가 얹히고, 유닉스 소켓용 라우터는 같은 라우트를 인증 계층 없이 노출한다 — 두 문의 차이가 라우터 구성 단계에서 갈린다. 미들웨어는 헤더 토큰과 쿠키 토큰을 각각 추출해 둘 중 하나라도 맞으면 통과시키고(OR 판정), 둘 다 없거나 틀리면 인증 실패로 응답한다. 상태 변경 메서드에 대해서는, 헤더 토큰으로 통과한 경우가 아니라면 Origin/Referer 와 Host 의 권한 부분(authority)이 일치하는지를 추가로 검사한다. 토큰은 데몬 기동 시 생성되어 AppState 가 보유하고 파일로 기록된다. 통합 테스트 등 토큰 파일 없이 도는 환경을 위해 인증을 끄는 환경 변수 스위치가 있다.
