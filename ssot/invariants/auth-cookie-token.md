## 제약

웹 대시보드가 데몬에 보내는 요청의 인증은 두 채널을 갖되 우선순위가 정해져 있다.

- **기본 채널 — 세션 쿠키**: 데몬은 웹 화면을 처음 내려줄 때 브라우저가 보호하는(자바스크립트가 읽을 수 없는) 세션 쿠키를 함께 발급한다. 이 쿠키가 이후 모든 요청에 자동으로 실려 인증된다. 이 쿠키는 CLI 가 별도로 읽어 쓰는 토큰과 같은 비밀값을 담고 있으며, 토큰 파일을 직접 읽을 수 없는 브라우저를 위한 진입(부트스트랩) 채널이다.
- **폴백 채널 — 헤더 토큰**: 개발 중에는 화면(개발 서버 포트)과 데몬(데몬 포트)이 서로 다른 포트에 있어 쿠키가 자동으로 흐르지 못할 수 있다. 이때를 위해, 사용자가 한 번 입력해 브라우저 로컬 저장소에 보관해 둔 토큰을 인증 헤더로 함께 보내는 방식을 폴백으로 둔다. 데몬이 토큰 검사를 켠 환경에서 의미를 가진다.

순서가 핵심이다 — 쿠키가 정상 채널이고, 헤더 토큰은 쿠키가 닿지 못하는 교차 포트 개발 상황의 보완책이다.

## 깨지면 무슨 일이 일어나나

쿠키 채널만 있고 폴백이 없으면, 화면과 데몬이 다른 포트에 떨어져 있는 개발 환경에서 쿠키가 전달되지 않아 모든 요청이 인증 실패로 막힌다. 반대로 헤더 토큰을 기본으로 삼으면, 비밀값을 자바스크립트가 읽을 수 있는 저장소에 상시 의존하게 되어, 데몬이 일부러 브라우저 보호 쿠키를 쓰는 이유(스크립트가 토큰을 읽지 못하게 함)가 무력화된다. 두 채널의 우선순위가 흐트러지면, 개발 편의를 위한 폴백이 운영의 기본 보안 자세를 갉아먹는다.

## 코드에서 어떻게 강제되나

웹의 네트워크 계층(`web/src/api.ts`)은 모든 요청에 자격 증명(쿠키)을 포함하도록 설정하고, 동시에 헤더 토큰 묶음을 함께 펼쳐 보낸다 — 토큰이 없으면 헤더 묶음이 비어 있어 쿠키만 작동한다. 토큰의 읽기/쓰기와 헤더 구성은 인증 모듈(`web/src/lib/auth.ts`) 한 곳에 모여 있고, 토큰은 로컬 저장소를 떠나지 않는다(분석·오류 보고로 새지 않음). 코드 주석은 쿠키가 기본 부트스트랩 채널이고 헤더 토큰은 교차 포트 개발용 폴백임을 명시한다. 쿠키 발급과 토큰 검사는 데몬이 수행하므로, 이 인증 약속은 웹↔데몬 경계를 가로지른다.
