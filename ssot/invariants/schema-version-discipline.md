## 제약

데몬이 SQLite 스키마를 진화시키는 방식은 세 자원의 합의로 정의된다 — (1) 데몬이 다룰 수 있는 **최대 스키마 버전 상수**, (2) 적용 순서대로 나열된 **마이그레이션 목록**, (3) 각 버전에 대응하는 **SQL 파일**. 이 셋은 언제나 서로 일치해야 한다. 새 버전을 도입할 때 SQL 파일 추가·목록 항목 추가·최대 버전 상수 갱신이 **같은 커밋에서 함께** 일어나야 하며, 셋 중 하나만 바뀌면 안 된다.

두 가지 단방향성도 이 제약에 포함된다.

- **미래 거부**: 디스크에 있는 DB 의 스키마 버전이 이 데몬 바이너리가 아는 최대 버전보다 높으면, 데몬은 그 DB 를 열기를 거부한다. 즉 더 새로운 버전이 만든 DB 를 옛 데몬이 함부로 건드리지 않는다(다운그레이드 가드).
- **과거 불변**: 이미 누군가의 DB 에 적용된 과거 마이그레이션의 SQL 본문은 절대 사후에 고치지 않는다(주석·개행 변경조차). 컬럼·테이블을 바꿔야 하면 옛 파일을 수정하는 게 아니라 **새 버전의 마이그레이션을 추가**한다. 마이그레이션 목록의 항목을 제거하거나 순서를 바꾸거나, 새 버전을 기존 번호 사이에 끼워넣는 것도 금지된다(버전 번호는 단조 증가, 빈 번호도 재사용 금지).

## 깨지면 무슨 일이 일어나나

세 자원이 어긋나면 신규 DB 가 깨진 스키마로 기동된다 — 예컨대 최대 버전 상수만 올리고 SQL 파일·목록을 추가하지 않으면, 데몬은 "이 버전까지 가능"이라 믿지만 정작 그 버전을 만드는 SQL 이 없다. 과거 마이그레이션 본문을 사후 편집하면, 옛 본문으로 이미 마이그레이션을 통과한 사용자 DB 와 새 본문으로 기동된 DB 사이에 스키마가 갈려, 같은 버전 번호인데 실제 구조가 다른 상황이 된다 — 가장 추적하기 어려운 종류의 데이터 불일치다.

## 코드에서 어떻게 강제되나

미래 버전 거부만 데몬이 코드로 자동 강제한다 — 기동 시 디스크 스키마 버전이 최대 버전 상수보다 크면 `SCHEMA_DOWNGRADE_REFUSED` 로 기동을 멈춘다. 적용 루프는 이미 적용된 버전은 건너뛰고 그 이상만 트랜잭션 안에서 순서대로 적용한다.

나머지(세 자원 동기, 과거 본문 불변, 순서 불변)는 **자동 강제 장치가 없다** — 컴파일러가 통과시키므로 작성자의 규율과 코드 리뷰에 의존한다. 구체적으로 다음 검사가 부재함이 룰 문서에 명시되어 있다: 마이그레이션 목록의 마지막 버전과 최대 버전 상수가 일치하는지 보는 컴파일 타임 단언, 디렉터리의 SQL 파일 목록과 목록 배열의 파일명이 일치하는지 보는 테스트, 과거 본문이 변경됐는지 감지하는 해시 게이트가 모두 없다.
