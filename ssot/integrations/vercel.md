## 무엇과 연동하나

Clawket 의 공개 랜딩(마케팅) 페이지는 **Vercel** 이라는 외부 정적 호스팅 서비스 위에서 운영된다. 연결 방식은 "Git 통합" 이다 — 랜딩 페이지 소스가 들어 있는 GitHub 저장소를 Vercel 프로젝트에 한 번 연결해 두면, 그 뒤로는 main 브랜치에 변경이 올라올 때마다 Vercel 이 그것을 스스로 감지한다. 감지하면 Vercel 자체 빌드 워커에서 의존성 설치와 빌드를 수행하고, 만들어진 정적 산출물(HTML·자바스크립트·이미지 등)을 운영 주소로 발행한다.

별도의 "배포용 스크립트" 가 저장소 안에서 Vercel 로 파일을 밀어 넣는 구조가 아니다. 저장소 쪽 CI 는 빌드가 깨지지 않는지 확인하고 산출물을 점검용으로만 보관하며, **실제 운영 배포는 Vercel 이 자기 환경에서 다시 빌드해 처리한다.** 즉 빌드 명령·산출물 폴더·Node 버전 같은 빌드 환경 설정은 Vercel 프로젝트 설정 화면에 들어 있고, 저장소가 들고 있는 것은 발행 결과의 동작 규칙(응답 헤더와 경로 우회 규칙)뿐이다.

이 사이트는 누구나 접근 가능한 공개 페이지로 운영된다 — 접근을 막는 보호 장치(로그인 게이트 등)는 꺼져 있어 운영 주소와 미리보기 주소 모두 공개로 열려 있다.

## 구현 위치 (provenance)

운영의 동작 규칙은 랜딩 저장소의 배포 설정 파일(`landing/vercel.json`)에 들어 있고, 이것이 발행물의 정본이다. 여기에는 두 종류의 규칙이 있다.

- **경로 우회 규칙**: 랜딩 페이지는 한 개의 HTML 진입점 위에서 클라이언트 라우팅으로 여러 페이지를 보여 주는 단일 페이지 앱이다. 그래서 정적 자산·설치 스크립트·블로그/튜토리얼·확장자가 붙은 실제 파일 경로를 제외한 나머지 주소 요청은 모두 진입 HTML 로 되돌려, 브라우저 안의 라우터가 페이지를 그리게 한다.
- **응답 헤더 규칙**: 설치 스크립트를 셸 스크립트 형식으로 응답하도록 콘텐츠 타입을 고정하고 짧게 캐시하며, 정적 자산은 오래 캐시, 진입 HTML 은 캐시하지 않도록 하고, 사이트 전역에 보안 기본값(콘텐츠 타입 추측 금지, 레퍼러 정책, 권한 정책)을 건다.

운영 주소·배포 파이프라인의 전체 그림과 "빌드는 Vercel 이 자기 환경에서 다시 돌린다" 는 설명은 랜딩 저장소의 안내 문서(`landing/CLAUDE.md`)에 정리되어 있다. 이 연동을 사용하는 내부 컴포넌트는 clawket 본 제품(CLI·데몬·웹 대시보드)이 아니라 **별도의 랜딩 페이지 산출물**이므로, 본 SSOT 인벤토리에 대응하는 컴포넌트 노드가 없어 integratesWith 는 비워 둔다(OPEN).

## 불변식

- 운영 배포는 사람의 별도 조작 없이 main 브랜치 push 만으로 트리거된다 — 따라서 main 에 올라가는 것은 곧 운영에 나가는 것이다(코드 변경 시 commit/push 를 함부로 하지 않아야 하는 이유).
- 설치 스크립트는 셸 스크립트 콘텐츠 타입으로 응답되어야 하고, 단일 페이지 앱 경로 우회 규칙은 새 페이지 경로가 추가될 때 그 경로를 가로채지 않도록 유지되어야 한다. 이 동작 규칙은 발행물의 정본 설정 파일이 책임진다.

## 영향 범위

이 연동의 변경(빌드 설정·경로 우회·헤더 규칙)은 랜딩 페이지의 노출·라우팅·설치 스크립트 서빙 표면에 파급된다. 다만 그 표면은 모두 랜딩 산출물 내부이며, 본 SSOT 인벤토리에 등재된 clawket 제품 개념·화면·불변식과 직접 연결되는 대상은 확인되지 않았다(impacts 는 OPEN).

설치 스크립트가 받아오는 바이너리 자체의 정본은 GitHub Releases 경로이므로, 사용자 설치 흐름 관점에서 두 연동이 맞물린다(relatesTo 참조).
