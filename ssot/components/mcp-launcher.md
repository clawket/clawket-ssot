## 책임

MCP 런처는 Clawket 플러그인이 Claude Code에 MCP(지식 검색용 도구 모음) 서버를 노출할 때 가장 먼저 실행되는 얇은 시동 스크립트다. 이 런처가 존재하는 이유는 Claude Code의 동작 순서 때문이다. Claude Code는 플러그인이 켜지는 순간, 어떤 세션 시작 절차보다도 먼저 플러그인의 MCP 서버를 띄우려 한다. 그런데 Clawket의 실제 MCP 기능은 별도로 내려받는 CLI 바이너리 안에 들어 있어서, 플러그인이 처음 켜지는 그 시점에는 바이너리가 아직 없을 수 있다.

런처는 이 빈틈을 메운다. MCP 서버를 직접 실행하기 전에, 먼저 설치 보장 절차를 한 번 호출해 CLI를 비롯한 바이너리가 준비되어 있는지 확인하고, 그 다음 CLI의 MCP 모드를 자식 프로세스로 띄워 입출력을 그대로 연결한다. 즉 런처 자신은 MCP의 실제 기능을 하나도 갖고 있지 않고, "준비 보장 → 위임 실행"이라는 두 가지 역할만 맡는다.

런처는 설치 로직을 자체적으로 다시 구현하지 않는다. 세션 시작 훅이나 수동/CI 설치 진입점이 쓰는 것과 똑같은 단일 설치 보장 절차(설치 게이트)를 그대로 불러 쓴다. 덕분에 "어떻게 설치되는가"에 대한 진실은 한 곳에만 존재하고, 런처는 그 진실을 호출만 한다.

## 경계와 의존

런처는 플러그인 셸 안의 Node 스크립트로 동작하며, 다음에 의존한다.

- CLI 바이너리: 런처가 궁극적으로 띄우려는 대상이다. 런처는 CLI를 MCP 모드로 실행해 표준입출력을 물려준다. 환경 변수로 바이너리 경로를 지정할 수 있고, 지정이 없으면 플러그인 루트 아래의 표준 위치를 운영체제별 실행 파일명으로 찾는다.
- Claude 어댑터(공유 핸들러): 런처는 어댑터가 노출하는 설치 보장 절차를 직접 호출한다. 설치 책임을 어댑터에 위임함으로써 설치 진실의 단일 출처를 유지한다.
- 설치 게이트: 런처가 호출하는 설치 보장 절차가 바로 이 게이트의 멱등 설치 로직이다. 게이트가 이미 설치가 끝났다고 판단하면 런처의 호출은 사실상 무동작으로 빠르게 통과한다.

런처는 외부에 API를 제공하지 않으며, 다른 컴포넌트의 HTTP API를 직접 호출하지도 않는다. 설치 보장이 실패하더라도 런처는 즉시 중단하지 않고 경고만 남긴 뒤 바이너리 존재 여부로 최종 판단한다. 바이너리가 끝내 없으면 오류 메시지를 남기고 비정상 종료한다.

## 통신 패턴

런처는 두 방향의 흐름을 잇는다. 위로는 Claude Code가 플러그인 등록 파일을 통해 "node로 이 런처를 실행하라"는 지시로 런처를 띄운다(MCP 연동). 아래로는 런처가 CLI를 자식 프로세스로 띄우고 표준입력·표준출력·표준오류를 그대로 상속시켜, Claude Code와 CLI 내장 MCP 서버 사이의 stdio 통로를 사실상 그대로 통과시킨다. 자식 프로세스가 시그널로 종료되면 런처 자신도 같은 시그널로 종료하고, 정상 종료 코드면 그 코드를 그대로 물려받아 종료한다. 즉 런처는 통신 내용에 개입하지 않는 투명한 중계자다.

## 하위 서브패키지 (책임 단위)

런처는 단일 파일 스크립트로, 별도의 하위 서브패키지를 두지 않는다. 설치 보장 로직은 자체 구현이 아니라 Claude 어댑터의 공유 핸들러에 위치하므로, 런처 본체는 "플러그인 루트 해석 → 설치 보장 호출 → 바이너리 경로 확인 → CLI MCP 모드 위임 실행"의 순차 흐름만 담는다.
