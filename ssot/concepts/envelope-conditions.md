## 정의

실행 봉투에는 그 태스크가 **시작될 자격이 있는지**를 따지는 전제조건(precondition)과, **끝났다고 인정해도 되는지**를 따지는 완료조건(postcondition)을 적어둘 수 있다. 데몬은 이 조건들을 사람이 아니라 기계가 그 자리에서 검사한다. 전제조건은 태스크가 진행 상태로 들어갈 때, 완료조건은 완료 상태로 넘어갈 때 평가된다. 조건 목록을 위에서부터 순서대로 보다가 **하나라도 어긋나면 곧바로 멈추고** 그 어긋난 조건을 그대로 오류에 실어 돌려준다(상태 전환은 일어나지 않는다). 모든 조건이 통과해야만 전환이 성사된다.

조건은 다섯 가지 검사 항목 중 하나로 표현된다.

- **다른 태스크의 상태 확인** — 지정한 태스크(ULID 또는 사람이 읽는 티켓 번호)의 현재 상태가 기대한 값(예: "완료됨")과 같은지 본다. 그 태스크가 없으면 "찾을 수 없음"으로 실패한다.
- **파일 존재 확인** — 지정한 경로의 파일이 디스크에 있는지 본다. 상대 경로면 봉투가 가리키는 대상 저장소 위치를 기준으로 풀어서 확인하며, 그 기준 위치가 없으면 풀 수 없어 실패한다. 절대 경로는 그대로 본다.
- **지식 존재 확인** — 주어진 조건(종류·제목에 포함된 문구·연결된 태스크)에 맞는 지식 항목이 최소 한 건이라도 있는지 본다.
- **데몬 건강 확인** — 항상 통과한다. 이 조건을 평가하고 있다는 것 자체가 데몬이 HTTP 요청을 처리 중이라는 뜻이므로, 살아 있음이 자명하기 때문이다.
- **임의 명령 실행** — 지정한 명령을 정해진 제한 시간 안에 실행하고, 종료 결과가 기대한 성공/실패 방향과 맞는지 본다(예: 테스트나 빌드 검사를 통과해야만 완료 인정). 제한 시간을 넘기면 강제 종료하고 "시간 초과"로 실패한다.

알 수 없는 종류의 조건이거나, 조건에 종류 표시 자체가 빠져 있으면 그 역시 실패로 처리된다.

## 엔티티 (DB)

조건은 별도 테이블이 아니라 **실행 봉투 안에 담긴 두 개의 목록**(전제조건 배열·완료조건 배열)으로 존재한다. 각 항목은 "종류"를 가진 작은 구조로, 종류에 따라 필요한 추가 값(대상 태스크·기대 상태·파일 경로·지식 필터·명령과 인자·제한 시간·기대 성공 여부 등)이 달라진다. 평가 시에는 봉투가 가리키는 대상 저장소 경로를 함께 넘겨받아, 상대 경로 파일 확인과 명령 실행의 작업 디렉터리 기준으로 쓴다. 다른 태스크 상태·지식 존재 확인은 같은 로컬 DB의 태스크·지식 기록을 조회해 판정한다.

## API 표면

직접 호출되는 별도 엔드포인트가 아니라, **태스크 상태 갱신 처리 안에서 호출되는 검사 단계**다. 상태가 진행으로 바뀔 때 전제조건이, 완료로 바뀔 때 완료조건이 자동으로 돌아간다. 조건이 어긋나면 충돌(HTTP 409)로 응답하며, 어긋난 조건의 원본 내용을 오류 본문의 상세 항목에 그대로 담아 호출자가 무엇이 막혔는지 알 수 있게 한다.

## 불변식

- 조건 평가는 첫 실패에서 즉시 중단되며, 그 시점까지 통과한 조건만 검사되고 이후 조건은 보지 않는다(짧은 회로 평가).
- 조건이 하나라도 실패하면 해당 상태 전환은 일어나지 않는다.

## 구현 위치 (provenance)

- 다섯 종류 조건의 평가 로직 전체와 순차·짧은회로 평가: `daemon/src/envelope/conditions.rs`
- 호출 지점(진행 전환 시 전제조건, 완료 전환 시 완료조건): 같은 파일 머리주석이 태스크 갱신 처리에서 호출됨을 명시.
