## 맥락 (Context)

웹 대시보드는 한 화면 안에서 여러 축의 상태를 동시에 다룬다. 사용자는 (1) 여러 등록 프로젝트 중 하나를 고르고, (2) 요약·보드·백로그·타임라인·위키 다섯 화면 중 하나를 보며, (3) 특정 태스크·유닛·플랜의 상세를 옆에서 펼쳐 본다. 이 세 가지를 어디에 보관하느냐에 따라 "새로고침하면 보던 화면이 사라지는가", "북마크/링크 공유로 같은 화면을 다시 열 수 있는가", "뒤로가기가 직관적으로 동작하는가" 가 갈린다.

또한 과거 버전에는 별도의 "Plans" 화면이 있었으나 이후 사이드바의 플랜 트리로 흡수되었다. 그 시절에 만들어진 북마크나, 브라우저에 저장된 "마지막으로 본 화면" 값이 그대로 살아 있어, 그 경로로 들어왔을 때 화면이 깨지지 않아야 한다.

## 결정 (Decision)

화면 상태를 컴포넌트 내부 변수가 아니라 **주소창 경로 자체**에 담는다. 경로는 `/{프로젝트}/{뷰}` 형태가 기본이고, 상세 항목을 펼친 상태는 `/{프로젝트}/{뷰}/{타입}/{ID}` (타입 = task·unit·plan)로 확장한다. 화면을 그릴 때는 현재 경로를 거꾸로 해석해 프로젝트·뷰·상세 항목을 끌어내며, 화면 전환·프로젝트 선택·상세 열기/닫기는 모두 새 경로로 이동시키는 방식으로 처리한다. 즉 라우터가 곧 상태 저장소다.

폐기된 옛 경로(예: 과거 "plans" 화면 경로)는 삭제하지 않고, 들어오는 즉시 현재 대응 화면(요약)으로 조용히 다시 보내는 호환 장치로 남긴다. 경로 뒤쪽에 붙은 상세 항목 식별자는 전환 과정에서 보존한다.

## 근거와 결과 (Consequences)

- **단일 진실원 원칙**: 화면 상태가 주소에만 존재하므로 "내부 변수와 주소가 어긋나는" 부류의 버그가 구조적으로 사라진다. 새로고침·뒤로가기·링크 공유가 모두 같은 경로 해석을 거치므로 동일 결과를 보장한다.
- **링크 공유성**: 사람 운영자가 특정 태스크 상세나 특정 보드 화면의 주소를 그대로 공유하면 상대도 같은 화면을 연다. 작업 협업·리뷰에 직접 도움이 된다.
- **하위 호환 비용**: 폐기 경로를 영구 보존(전환 장치)하기로 했으므로, 화면 구조를 바꿔도 과거 북마크/저장값이 깨지지 않는다. 대신 전환 규칙이 코드에 계속 남는다는 유지 비용을 받아들인다.
- **영향 범위**: 다섯 화면 전체와 상세 드로어가 이 규칙 위에서 동작한다. 화면을 추가·삭제할 때는 경로 어휘(허용된 뷰 이름 집합)와 전환 규칙을 함께 갱신해야 한다.
