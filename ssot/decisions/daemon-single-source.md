## 맥락 (Context)

태스크를 하위 태스크로 쪼개는 "분해 제안" 과, 실행 봉투(태스크가 어떻게 수행되어야 하는지를 담은 계약)의 "유효성 검증" 은 단순 표시가 아니라 규칙이 개입하는 판단이다. 분해 제안은 봉투의 성공 기준(success_criteria)과 분해 정책에서 후보 하위 태스크를 끌어내는 일이고, 봉투 검증은 정해진 구조 규칙에 맞는지를 따지는 일이다.

이 판단을 화면(웹 클라이언트) 쪽에서 자체적으로 계산하게 두면, 같은 태스크를 두고 CLI 나 LLM 에이전트(MCP)가 내린 결과와 화면이 보여주는 결과가 달라질 위험이 있다. 동일 입력에 대해 도구마다 다른 답을 주면 사용자는 무엇을 믿어야 할지 알 수 없고, 규칙이 바뀔 때마다 모든 클라이언트를 똑같이 고쳐야 하는 중복 유지보수가 생긴다.

## 결정 (Decision)

분해 제안·봉투 검증·하위 태스크 생성을 웹 클라이언트가 흉내 내지 않는다. 모두 데몬의 전용 엔드포인트에 요청을 보내고, 화면은 데몬이 돌려준 결과(제안 목록·정책 위반 항목·검증 판정)를 **그대로** 표시·반영하는 역할만 맡는다. 분해 패널은 데몬이 준 제안을 받아 사용자가 고르고 순서를 정해 다시 데몬에 하위작업으로 등록하며, 봉투 편집 화면은 입력이 바뀔 때마다 데몬 검증 엔드포인트에 물어 그 판정을 보여준다. 클라이언트가 보는 분해 결과의 형상은 CLI·MCP 의 분해 도구가 노출하는 것과 같은 모양으로 맞춘다.

## 근거와 결과 (Consequences)

- **단일 진실원 원칙(규칙의 위치)**: 분해·검증 규칙을 데몬 한 곳에만 두므로, CLI·MCP·웹 어느 입구로 들어와도 같은 입력에 같은 판단이 나온다. 규칙이 바뀌어도 데몬만 고치면 모든 클라이언트에 일괄 반영된다.
- **실패 시나리오 방지**: "화면에서는 통과인데 CLI 로는 거부" 같은 도구 간 불일치, 그리고 규칙 변경 시 클라이언트마다 따로 고치다 한 곳을 빠뜨리는 누락을 막는다.
- **클라이언트 단순화**: 웹은 규칙 엔진을 들고 있지 않고 요청·표시만 담당하므로 화면 코드가 얇아진다. 대신 매 검증마다 데몬 왕복이 필요하다 — 봉투 편집의 실시간 검증은 입력이 멈춘 뒤 잠깐 기다렸다 보내는 방식으로 호출 빈도를 다듬는다.
- **영향 범위**: 분해 제안 패널, 봉투 편집·검증 화면, 하위 태스크 생성 흐름이 모두 데몬 응답에 의존한다. 데몬이 닫혀 있으면 이 기능들은 동작하지 않으며, 화면은 데몬 응답의 오류를 사용자에게 그대로 노출한다.
