## 무엇인가

데스크탑 모노레포는 데스크탑 앱과 그 앱이 사용하는 공유 UI 패키지를 하나의 저장소에서 함께 관리하는 pnpm 워크스페이스다. 워크스페이스는 두 갈래로 나뉜다 — 애플리케이션 묶음(apps)과 재사용 패키지 묶음(packages). 현재 애플리케이션 쪽에는 데스크탑 앱(@clawket/desktop)이, 패키지 쪽에는 공유 UI/디자인 시스템(@clawket/ui)이 들어 있다. 데스크탑 앱은 공유 UI 패키지를 워크스페이스 내부 의존성으로 끌어다 쓴다.

빌드는 순서가 고정되어 있다. 먼저 패키지 묶음(공유 UI)을 빌드하고, 그다음 데스크탑 앱을 빌드한다. 부품이 먼저 완성되어야 그 부품을 쓰는 앱이 제대로 빌드되기 때문이다.

## 누구를 위한 것인가

직접적인 사용자는 데스크탑 앱을 쓰는 사람 운영자(persona.human-operator)지만, 이 모노레포 자체는 그 앱과 디자인 시스템을 만드는 개발 작업의 구조다. 모노레포로 묶는 이유는 화면 부품(디자인 시스템)과 이를 소비하는 앱을 한 버전 흐름 안에서 같이 진화시키기 위함이다. 부품을 고치면 앱이 같은 저장소에서 즉시 그 변경을 받는다.

## 서비스 영역

이 플랫폼이 담는 워크스페이스(서비스 모듈)는 다음 두 갈래다.

- **데스크탑 앱(apps/desktop, @clawket/desktop)**: Tauri 셸 + React 화면으로 구성된 실행 애플리케이션. 공유 UI 패키지를 의존성으로 가져온다. 별도 플랫폼 노드(platform.desktop)로 다룬다.
- **공유 UI / 디자인 시스템(packages/ui, @clawket/ui)**: 데스크탑 앱(과 웹 화면)이 함께 쓰는 컴포넌트와 디자인 토큰을 제공하는 재사용 패키지. 빌드 시 항상 먼저 빌드되며, 컴포넌트 카탈로그(스토리북) 표면도 이 패키지에서 제공한다.

## 접근 매트릭스 (역할 → 서비스)

모노레포는 빌드·개발 구조이지 런타임 권한 경계가 아니므로 역할별 접근 분리가 없다. 두 워크스페이스의 관계는 권한이 아니라 의존 방향으로 정리된다 — 데스크탑 앱이 공유 UI 패키지를 소비하는 단방향 의존이고, 빌드는 공유 UI → 데스크탑 앱 순서로 흐른다.

| 워크스페이스 | 역할 | 의존 방향 |
|--------------|------|-----------|
| 공유 UI(@clawket/ui) | 부품 제공자 | 데스크탑 앱이 이것을 소비 |
| 데스크탑 앱(@clawket/desktop) | 부품 소비자 | 공유 UI에 의존 |

## 기술 스택 (제품 맥락)

- **워크스페이스 도구**: pnpm 워크스페이스. 두 묶음(apps/*, packages/*)을 한 저장소에서 관리한다.
- **빌드 오케스트레이션**: 루트에서 공유 UI 패키지를 먼저 빌드한 뒤 데스크탑 앱을 빌드하도록 순서를 고정. 린트·타입체크·테스트는 워크스페이스 전반에 재귀 실행된다.
- **공유 UI 패키지**: React 19 기반 컴포넌트와 디자인 토큰을 빌드 산출물로 내보내고, 스토리북으로 컴포넌트를 문서화한다.
- **데스크탑 앱**: Tauri 2 셸 + React 19 화면(platform.desktop 참조).
